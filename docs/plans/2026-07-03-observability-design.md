# Brain Observability — The Journal

> Status: design proposal · Date: 2026-07-03 · Author: design handoff response
> Sources: `docs/prd.md` (v0.3), `docs/superpowers/specs/2026-06-21-activity-event-backbone-design.md`,
> `docs/specs/2026-07-03-brain-api-review.md` (F2/F5/F6), `docs/specs/2026-07-03-measurement-v2-spec.md` (§3.7), `src/web/` as of `b26c2bf`.
> This is a design doc. It specifies instrumentation contracts but changes no code.

---

## 1. Concept

**Brain already narrates other people's work. The Journal is Brain narrating itself.**

The observability surface is a single reverse-chronological **Journal**: a river of *episodes* — sessions digested, agents consulting Brain, observations noticed, approvals granted, eval runs scored, learnings landed — each rendered as a sentence you can open into its atoms. Above the river sits the **Pulse**: one narrated paragraph answering "what happened since you last looked," where every clause is a door into the river, filtered.

Three commitments, stated up front:

1. **Episodes, not events.** The `activity_events` table is the substrate, never the display unit. A session is one episode containing forty beats; a digest run is one episode; an approval batch is one episode. Nobody reads 40 rows; everybody reads "Claude worked 47 minutes on MCP instrumentation, consulted Brain 5×, raised 2 observations."
2. **One river, no swimlanes.** The handoff frames actors as "lanes." I reject the lane model: the interesting lanes are sparse (MCP consults, eval runs), sparse lanes render as dead whitespace, and the story *interleaves* — an agent consulting Brain mid-session belongs **inside** that session's episode, not parallel to it. Actors are distinguished by containment, glyph/color, and filters — never by horizontal position. This is also the team-scale answer: a new teammate is a new actor value and a new filter chip, not a new lane.
3. **Analysis is a lens on chronology, not a second place.** No charts page. Aggregates live in the Pulse and in per-episode rollups; the gesture between analysis and chronology is symmetric drill: click a number → river filters to its evidence; select a river range → right panel summarizes it (and the existing chat continues from there — the established narrative-as-chat direction, applied to the system itself).

The delight mechanism is honest: the same observation layer that watches development watches Brain. The Pulse sentence is generated by the machinery the product sells.

## 2. Relationship to the existing dashboard

**Work with it — and take its front door.**

- **Journal replaces `Overview`** as the landing view. Overview today is a static rollup; the Journal answers the same "where do things stand" question but with time and agency in it.
- **Features / FeatureDetail stay** exactly as the destination for "understanding" (the analysis-of-record per Feature). Journal episodes deep-link into them.
- **ReviewQueue evolves** into the Review Deck (§5.3) in phase 2; the phase-1 Journal reuses its endpoints untouched.
- **Sessions / SessionDetail stay** as the drill target for session episodes; the standalone Sessions list becomes redundant over time but is not removed by this design.
- **Knowledge Tree / Topics get zero investment.** Per API-review F1, Topic is the retired ontology. The Journal speaks Feature and Session only.
- The existing `/api/timeline` (git commits + brain versions) is **not** the timeline. Commits are context garnish (§4.5), and `brain_versions.commit_sha` being empty everywhere means brain versions currently anchor to nothing — the Journal does not depend on them.

## 3. Information architecture

```
Journal (landing)
├── Pulse ............... "since you last looked" — narrated stats strip
├── River ............... reverse-chron episodes, grouped by day chapters
│   ├── Episode ......... session | digest run | observe sweep | eval run
│   │                     | approval batch | learning | (later: PR, ticket…)
│   │   └── Beats ....... moments, MCP consults, observations, outcomes
│   └── "last looked" line
├── Ask the Journal ..... right panel: selection-aware chat + range analysis
└── Deep links .......... episode → SessionDetail / FeatureDetail / Review Deck

Review Deck (from Pulse or nav) — the human gate, redesigned (§5.3)
Features / FeatureDetail — unchanged, the per-Feature analysis of record
```

**First 5 seconds** (the handoff's opening question): the Pulse. One paragraph, machine-written, clause-per-signal:

> *Since Tue 18:40 — 3 sessions digested · agents consulted Brain 14× (2 misses) · Brain noticed 6 things, **4 await your review (~2 min)** · eval last ran 9 days ago · Feature "Activity events" learned 2 constraints.*

Design rules for the Pulse: it is a **sentence, not a wall of stat cards**; it always names the bottleneck (pending review) with a time estimate; it always admits staleness ("eval last ran 9 days ago" — dark lanes are shown as dark, not hidden); every clause is clickable and filters the river. "Since you last looked" is a stored read-cursor (localStorage in phase 1, per-user server-side later — that cursor is the only per-user state the team version needs).

## 4. The timeline model

### 4.1 Three zoom levels

| Level | Unit | Answers | Rendering |
|---|---|---|---|
| **Chapter** | a day (week when zoomed out) | "what kind of day was it?" | date header + one summary line + episode chips |
| **Episode** (default) | a grouped body of work | "what happened?" | card: actor glyph · title sentence · rollup counts · expand |
| **Beat** | a single `activity_event` | "what specifically?" | timestamped line inside an expanded episode |

### 4.2 Grouping — read-side, no schema change for display

Episodes are computed by a read-side grouper over `activity_events`. **No `episode_id` column.** Rules, in precedence order:

1. **`session_id` present** → beat of that session's episode. This is how MCP consults, moments, transitions, outcomes, and session-scoped observations all fold into one card. (Legacy events are grouped by `source_type ∈ {moment, transition, outcome, narrative}` + `session_id`, since today's categories are unnamespaced — see §7.1.)
2. **`metadata.runId` present** → beat of that run's episode (digest runs, observation sweeps, eval runs). This is a *contract requirement* on future emitters (§7.3), not a schema change.
3. **Category-prefix + time-proximity fallback** → e.g. `review:*` events by the same actor within 10 minutes collapse into one "You approved 3 observations" episode.
4. **Singleton** → an event with no grouping key is its own episode (fine: an unattached observation *should* stand alone and demand attention).

### 4.3 Ordering

Episodes are **newest-first** (a journal you catch up on, not a log you scroll to the end of). Beats inside an expanded episode read **oldest-first** — once you're inside a story, it reads forward.

### 4.4 Actors without lanes

Actor identity renders as a left-margin glyph + label on each episode: `you` · `agent:claude-code` · `pipeline` · `observer` · `eval` (convention in §7.2). Filter chips (`all actors ▾`) are the "lane isolation" gesture — filtering to `observer` gives you the pure observation lane *on demand*, without paying whitespace for it permanently. Team scale: actors become `human:gilad`, `human:dana`, `agent:claude-code:dana` — the filter grows, the layout doesn't change.

### 4.5 Anchors and garnish

Day chapters carry lightweight context fetched at read time, **not stored as events**: git commits that day (the existing `/api/timeline` git-log pattern), branch names seen. Rationale: commits are already someone else's system of record (Principle 1 — Brain doesn't re-store work); storing them as events would double-write GitHub. When `brain_versions.commit_sha` starts being populated, brain-version markers join the garnish the same way.

### 4.6 Where future integrations land

A PR review, a Jira ticket transition, a Slack decision, an incident — each is just an episode: category `github:pr-merged` / `jira:ticket-moved` / `slack:decision` / `incident:opened`, actor `integration:<source>`, `feature_id` when resolvable, own glyph. The river's model doesn't change; PRD's integration table maps 1:1 onto episode kinds. Intent-evidence episodes (P2+) get a distinct visual accent so the eventual intent-vs-implementation interleaving is legible on the same river.

This screen is the anti-lane-soup argument made visible: the agent's Brain consults (`↳`), the pipeline's extracted moments (`◆✦⚠✓`), and the write-backs (`●`) are one interleaved story. A MISS beat is a product signal, not an error — `[why?]` opens the chat pre-seeded with that beat.

### 5.3 The Review Deck (the human gate)

The current ReviewQueue is a correct list. The Deck redesign rests on one thesis: **approval feels like a chore when it's filing, and like a joy when it's teaching — so show the student learning.**

```
┌ REVIEW · 4 pending · ~2 min ─────────────────────────────────────────────┐
│                                                                           │
│   2 of 4                    Feature: Activity events          constraint  │
│  ┌─────────────────────────────────────────────────────────────────────┐ │
│  │ "New emitEvents call sites must be wrapped in try/catch — event    │ │
│  │  emission may never fail the parent operation."                    │ │
│  │                                                                     │ │
│  │  noticed by agent:claude-code · Thu 11:30 session ("Wired MCP…")   │ │
│  │  evidence: "…wrapped the emit in try/catch matching                │ │
│  │  orchestrator.ts:88…"                                   [session →]│ │
│  │  ─────────────────────────────────────────────────────────────────│ │
│  │  if approved, agents entering src/pipeline/** are served:          │ │
│  │    constraints (2 → 3)                                             │ │
│  │      · events are self-contained; no joins at query time           │ │
│  │      · categories are freeform — never add an enum                 │ │
│  │    + · emitEvents call sites wrapped in try/catch          ← new   │ │
│  └─────────────────────────────────────────────────────────────────────┘ │
│                                                                           │
│    [A]pprove      [E]dit      [R]eject      [S]kip      [F]eature ↗       │
│                                                                           │
│  ✓ your last approval ("no enums on category") was served 4× since Tue    │
└───────────────────────────────────────────────────────────────────────────┘
```

Four mechanisms:

1. **One card center-stage, keyboard-first** (`A/E/R/S`) — triage cadence, not form-filling. Grouped by Feature so context loads once per run of cards.
2. **Provenance on the card** — who noticed it, during what, with the evidence quote. Requires API-review F5 (provenance stamping); the design makes F5's absence visible as an empty "noticed by" line, which is the right pressure.
3. **The understanding diff** — "if approved, agents are served: …← new". You see the *consequence* before granting it. This is what makes the gate feel like curation of a served product rather than inbox cleanup.
4. **The teaching receipt** — "your last approval was served 4×." Computed from `mcp:*` events (§7.3): approved observation → constraints served by `brain_enter`/`brain_feature_context` calls. Closes the loop; the human sees the brain get smarter *because of them*. This line is the single highest-delight-per-pixel element in the design.

Also: a **"nothing pending" state that celebrates** ("Brain is current — 12 observations promoted this week") rather than an empty inbox, and a Pulse time-estimate so review reads as a bounded coffee-sized task.

## 6. The analysis lens

Chronology → analysis: select (a Pulse clause, an episode, or a dragged day-range) → right panel switches from chat to a **window rollup**: consult hit-rate, misses by file-path, observations raised vs approved, struggle-moment density, top Features touched — each figure clickable back into the filtered river (analysis → chronology). Below the rollup, the chat is pre-seeded with the window, so "why the spike?" is one keystroke from any number. No standalone analytics page until a recurring question outgrows this lens; per-Feature analysis already has a home (FeatureDetail).

## 7. Instrumentation contract

Freeform categories stay (backbone rule, CLAUDE.md anti-pattern) — what follows are **conventions the render layer relies on**, enforced by usage and a read-side mapper, never by enums or CHECK constraints.

### 7.1 What exists today (and its problems)

| Emitted by | Category today | Problem for the Journal |
|---|---|---|
| `emit-events.ts` session summary | the freeform `sessionShape` (e.g. "exploration") | unnamespaced — indistinguishable from any other category; shape belongs in tags |
| `emit-events.ts` moments | `moment.type` | same; grouper must fall back to `source_type` |
| `emit-events.ts` | `transition`, `outcome` | same |
| observation layer / MCP writes | `observation:<kind>` + `review_status` | good — this is the convention to generalize |
| MCP reads | **nothing** (API-review F6) | the river's most product-relevant beats don't exist |
| approve/reject endpoints | **nothing** (only `review_status` update) | the human's own actions are invisible on the human's timeline |
| eval runner | **nothing** (measurement §3.7 unbuilt) | eval lane dark |
| digest / observe / export runs | **nothing** (only their outputs) | the pipeline has outputs but no presence |

**Timestamp finding (load-bearing):** `emit-events.ts` stamps every event `new Date()` at digest time — all beats of a session collapse to the digest instant, destroying intra-session chronology. Phase 1 works around it (session episodes positioned via `sessions.started_at/ended_at`; beats ordered by `causal_order`-equivalent metadata). The contract fix: emitters must stamp `timestamp` = when the thing *happened* when derivable (chunk timing for moments), else carry `metadata.occurredAt`; digest time lives in `created_at` already.

### 7.2 Conventions (all freeform, mapper-normalized)

- **Category:** `namespace:verb-or-kind` — `session:digested`, `mcp:enter`, `observation:constraint`, `review:approved`, `eval:run`, `digest:run`, `github:pr-merged`. Legacy unnamespaced events are mapped at read time (by `source_type`), not migrated (optionally backfilled later — open question Q1).
- **Actor:** `human:<handle>` · `agent:<platform>` (later `agent:<platform>:<handle>`) · `system:pipeline` · `system:observer` · `system:eval` · `integration:<source>`. This one convention *is* the team-scaling mechanism.
- **Summary:** one standalone, narratable sentence — the Journal renders it verbatim; "something happened" quality degradation is already a self-monitoring signal in the backbone spec.
- **Grouping:** any emitter producing >1 event per operation stamps a shared `metadata.runId` (uuid).
- **Feature link:** set `feature_id` whenever known — it is the pivot between Journal and FeatureDetail.

### 7.3 Events the design requires (net-new)

| Category | Actor | When | Required metadata | Powers | Phase |
|---|---|---|---|---|---|
| `mcp:<tool>` (`mcp:enter`, `mcp:search`, `mcp:feature-context`, …) | `agent:<platform>` | every Brain MCP call (F6) | `tool`, `outcome: hit\|candidates\|miss\|error`, `featureId?`, `latencyMs`, `servedObservationIds?`, `client`, `sessionId?` | consult beats, hit/miss Pulse stat, miss-analysis, **teaching receipt** | **1** |
| `review:approved\|rejected\|edited` | `human:<handle>` | approval endpoints | `observationId`, `featureId`, `kind`, `editDiff?` | "YOU approved…" episodes; the human visible on their own timeline | **1** |
| `eval:run` | `system:eval` | per (task×arm×run), measurement §3.7 | `runId`, `taskId`, `arm`, `etc`, `tokens`, `cvr`, `success` | eval episodes with verdict math | 2 |
| `eval:report` | `system:eval` | per full eval report | `runId`, pass-bar/kill-switch outcome | Pulse eval clause with a verdict, not just recency | 2 |
| `digest:run` | `system:pipeline` | per digest invocation | `runId`, `sessionIds`, `durationMs`, `llmCalls` | pipeline presence; digest-failure visibility | 2 |
| `observe:run` | `system:observer` | per observation sweep | `runId`, `windowSize`, `observationCount` | observer presence; "sweep found nothing" is itself informative | 2 |
| `feature:updated` | `system:pipeline` or `human:*` | Feature understanding/constraints/map change | `featureId`, `delta`, `sourceObservationId?` | "learned 2 constraints" Pulse clause; learning episodes | 2 |
| `brain:exported` | `system:pipeline` | `.repo/` export | `runId`, files written | export freshness | 2 |
| `session:started` / `session:ended` | `agent:<platform>` | daemon detects live session | `sessionId`, `cwd`, `branch` | live "now" episode atop the river | 3 |
| `<source>:<verb>` (github/jira/slack/incident) | `integration:<source>` | integration ingestion | source URL/ref, `featureId?`, evidence-kind: intent\|implementation | integration episodes (§4.6) | P2+ (PRD) |

All emissions use the existing failure-safe `emitEvents` try/catch pattern — instrumentation may never fail the instrumented operation.

## 8. Phased build plan

### Phase 1 — the river flows (2–4 days, demoable)

Read-side rendering over existing data, plus the two cheapest/highest-value emits.

1. **Emit `mcp:*` events** in `src/mcp/server.ts` tool handlers (F6 — small, failure-safe; this repo dogfoods its own MCP daily, so the lane lights up with real data immediately).
2. **Emit `review:*` events** in the approve/reject/edit endpoints (a few lines each).
3. **`GET /api/journal?repoId&since&actor&featureId`** — read-side grouper (§4.2), legacy mapping by `source_type`, session-episode timestamps from the `sessions` table (works around the digest-time collapse), Pulse stats via plain SQL.
4. **Journal page** — Pulse strip (template sentence from SQL stats, no LLM yet), day chapters, episode river with expandable session beats, unread line (localStorage cursor), inline approve/reject on pending observations (existing endpoints), deep links to SessionDetail/FeatureDetail/ReviewQueue. Journal becomes the default view.

**Demo script:** work a normal morning with the Brain MCP enabled → open the dashboard → the Pulse narrates the morning; expand the session episode and watch your agent's Brain consults interleaved with its moments; approve an observation without leaving the river.

### Phase 2 — the gate and the proof (≈1 week)

5. **Review Deck** (§5.3): keyboard triage, provenance card (needs F5 stamping), understanding-diff, teaching receipt (now computable — `mcp:*` events have a week of data).
6. **`eval:run`/`eval:report` emission** in the measurement-v2 runner + eval episode cards + Pulse eval clause.
7. **Run contract**: `digest:run`, `observe:run`, `feature:updated`, `brain:exported` with `runId`; fix `emit-events.ts` occurred-time stamping.
8. **Narrated Pulse & chapter lines**: Haiku over the window's episode summaries, cached per digest/sweep (not per page-load), template fallback.

### Phase 3 — live, lens, and team

9. **Live episode**: daemon emits `session:started/ended` + significant live beats; SSE pushes a "now" episode pinned atop the river. (Deliberately sparse — see Q4.)
10. **Analysis lens** (§6): range-select → rollup panel → pre-seeded chat.
11. **Integration landing** pattern proven with the first real source (GitHub PRs, per PRD P2), including the intent-evidence visual accent.
12. **Team**: server-side per-user read cursor, actor filter chips per person, per-actor Pulse ("what did Dana's agents learn this week").

## 9. Taste calls (explicit)

1. **No swimlanes, ever.** Containment (beats inside episodes) + filters replace parallel lanes. This is the design's central bet.
2. **Episodes are computed at read time.** No `episode_id` column, no display-driven schema. The `runId` metadata convention is the only concession, and it's contract, not schema.
3. **The Pulse is prose.** One paragraph with clickable clauses beats six stat cards; delight lives in the system speaking about itself in the voice it uses for everything else.
4. **Approval is teaching, and the UI must show the student learning.** The teaching receipt ("served 4× since Tuesday") justifies phase-1's `mcp:*` emission priority almost by itself.
5. **Newest-first river, oldest-first beats.** Catch up at the top; read stories forward once inside.
6. **Commits are garnish, not events.** Read-time git-log on day chapters; Brain doesn't re-store systems of record.
7. **Dark lanes render as honest staleness, not absence.** "Eval last ran 9 days ago" in the Pulse is a feature; hiding un-instrumented signals would let them stay dark.
8. **Topic surfaces get nothing.** The Journal is Feature/Session-keyed from day one, aligned with API-review F1.

## 10. Open questions

- **Q1 — Legacy categories: map forever or backfill once?** The read-side mapper handles unnamespaced legacy events indefinitely; a one-shot backfill (a `backfill-events.ts` already sits in the repo root) would simplify the grouper. Lean: map in phase 1, decide on backfill when the mapper grows a third special case.
- **Q2 — Pulse narration cost/latency.** Haiku per digest/sweep with caching is the plan; if Pulse reads feel stale between digests, does it re-narrate on a threshold of new events? Measure, don't guess.
- **Q3 — What is a "session" for MCP events from other repos?** `mcp:*` events carry `sessionId` only when the client passes it (F5's optional `sessionId`). Consults without one render as singleton episodes — acceptable, or does the daemon correlate them by cwd+time?
- **Q4 — Live granularity.** The daemon could stream every tool call; the design wants only `session:started/ended` + significant beats in `activity_events` (raw streams would swamp the table the Journal reads). Where exactly "significant" sits is unsettled — deliberately deferred to phase 3 with real daemon output in hand.
- **Q5 — Miss-driven map editing.** The mock chat in §5.1 offers "[add mapping →]" on a `brain_enter` miss — turning misses into one-click file↔Feature map fixes. Powerful, but it's a write path from analysis; does it need the same review gate as observations, or is map curation (explicitly manual per PRD) exempt?
- **Q6 — Retention/volume.** At team scale with `mcp:*` per call, the events table grows fast. Partitioning/pruning policy is out of scope here but should be decided before phase 3's live emission.
